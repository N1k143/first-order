# FirstOrder frontend

Next.js 16 · React 19 · TypeScript · CSS Modules. Дизайн: Golos Text и токены из Figma FirstOrder. Шрифт поставляется локально, без запросов к Google Fonts при сборке и просмотре.

## Запуск

```sh
npm ci
cp .env.example .env.local
npm run dev -- --hostname 127.0.0.1 --port 3120
```

Открыть http://localhost:3120. По умолчанию включён демонстрационный режим: данные и изменения сохраняются в localStorage этого браузера, серверная авторизация не вызывается.

## Подключение к backend

Backend реализует канонический контракт `/api/v1`, служебные маршруты и серверную авторизацию. Для запуска базы, миграций и Supabase Auth см. [backend/README.md](../backend/README.md).

Чтобы явно включить реальные данные, добавить в `.env.local`:

```dotenv
BACKEND_URL=http://127.0.0.1:18080
NEXT_PUBLIC_DATA_MODE=api
```

`BACKEND_URL` используется только сервером Next.js. Значение `NEXT_PUBLIC_DATA_MODE` входит в клиентскую сборку: после изменения перезапустить dev-сервер, а для production заново собрать приложение. В `.env.example` явно выбран демонстрационный режим; автоматического переключения нет.

Прокси сохраняет служебные маршруты и два API-контракта:

- `/health` и `/ready` → одноимённые служебные маршруты backend.
- `/api/v1/:path*` → `${BACKEND_URL}/api/v1/:path*`: канонический API со snake_case.
- `/api/:path*` → `${BACKEND_URL}/:path*`: совместимый с текущим frontend API, Auth и `/health`.

В API-режиме приложение начинает с пустого состояния, загружает `/me`, заказы и доступные пользователю избранное, контакты, портфолио и отклики. После успешных изменений обновляются состояние и открытые ресурсы. При ошибке запроса демонстрационные данные не подставляются.

## Авторизация и подтверждение почты

Регистрация, вход, выход, обновление сессии, восстановление пароля и подтверждение email обслуживаются Go backend через Supabase Auth. Сессия хранится в HttpOnly cookies. API-клиент отправляет cookies на тот же origin; после `401` выполняет одно общее обновление сессии для одновременных запросов и повторяет исходный запрос не более одного раза. Ошибки остальных мутаций автоматически не повторяются.

Для писем настроить backend `AUTH_REDIRECT_URL` на URL frontend `/auth/callback` и разрешить этот URL в Supabase Auth. Например, для локальной разработки: `http://localhost:3000/auth/callback`. Origin frontend должен входить в backend `ALLOWED_ORIGINS`; при локальном HTTP требуется `COOKIE_SECURE=false`, в production — HTTPS и защищённые cookies.

Callback принимает fragment с `access_token`/`refresh_token` либо параметры `token_hash`/`type`, сразу удаляет их из адресной строки и обменивает на серверную сессию. Восстановление ведёт на `/reset-password`, остальные успешные подтверждения — в кабинет компании (`/workspace`) или список откликов разработчика (`/applications`). Email после регистрации передаётся странице `/verify-email`, чтобы повторная отправка работала без активной сессии. Вход выбирает кабинет по серверному профилю и членству в компании; модератор попадает в `/companies`.

## Реализованный интерфейс и ограничения

В обоих режимах доступны главная, каталоги и карточки компаний/заказов, контакты, исправления и формы авторизации. В режиме API работают подтверждение почты, вход/выход, кабинет заказов компании, создание/публикация заказа, отклик, выбор исполнителя и личный список откликов. Главная показывает открытый заказ из текущего состояния.

В демонстрационном режиме также доступны новые личные кабинеты, редакторы профиля и портфолио, аватар, избранное, история контактов, настройки, редактирование компании и заказа, предпросмотр, участники, модерация и справочные страницы. Эти дополнительные кабинеты сохраняют примеры локально; неподключённые формы в режиме API показывают недоступность. Наличие серверного маршрута само по себе не означает, что соответствующая новая форма уже подключена. Приглашения участников и импорт не имитируют отправку или загрузку.

Существующий серверный цикл заказов сохранён при объединении веток. Подробные границы режимов — в [docs/implementation-status.md](docs/implementation-status.md), адаптер — в [docs/backend-integration.md](docs/backend-integration.md).

## Проверки

```sh
npm run typecheck
npm run lint
npm test
npm run build
npm start
```

После объединения веток прошли TypeScript, ESLint, production-сборки demo/API, 17 модульных тестов транспорта, полей и переходов статусов и 20 браузерных тестов деморежима. Транспорт проверяет общий refresh для одновременных запросов и ограничение повторов. В среде без разрешения на IPC для `tsx` тот же файл тестов запускается напрямую:

```sh
node --import tsx tests/api-client.test.ts
```

До объединения веток браузерная проверка серверного сценария прошла как с тестовыми ответами, так и на рабочем сайте с PostgreSQL. В финальном прогоне два аккаунта зарегистрированы через публичную форму, оба письма Gmail SMTP получены и оба адреса подтверждены настоящими ссылками. Затем за 12,1 с прошёл сценарий: вход компании → создание/публикация заказа → вход разработчика → отклик → выбор исполнителя → отображение принятого отклика. Подтверждение email оставалось обязательным; административное подтверждение не использовалось. Все записи финального тестового прогона и тестовые пароли удалены, отсутствие оставшихся записей проверено. Статус развёртывания и состав очистки — в [deploy/README.md](../deploy/README.md).

## Браузерные проверки

```sh
npx playwright install chromium
npm run test:browser
```

Можно использовать установленный Chrome: `CHROME_PATH=/usr/bin/google-chrome npm run test:browser`. Браузерные тесты запускают отдельную демонстрационную production-сборку на порту 3121 и проверяют главную, поиск, авторизацию, профиль и цикл заказов. Это проверки интерфейса, а не доставка реальных писем.

## Оформление кода

Prettier, EditorConfig и настройки VS Code задают многострочное форматирование. `npm run format:check` проверяет оформление; `npm run format` применяет его.

## Структура

- `src/app`: маршруты App Router, callback авторизации, layout и 404.
- `src/components/layout`: общие шапка и подвал.
- `src/features`: интерфейсы home, catalog, orders, workspace и auth.
- `src/lib/api`: запросы, ошибки, отмена, тайм-ауты, refresh и обновление ресурсов.
- `src/lib/state`: отдельное демонстрационное или серверное состояние.
- `src/types`: типы предметной области.
- `tests`: проверки API-клиента, схем полей, переходов статусов и браузерных сценариев.
- `tools/figma-export`: экспортёр макетов, не часть приложения.
- `docs/implementation-status.md`: состояние переноса и оставшийся объём.

## Явный production E2E

`playwright.production.config.ts` и `tests/production` содержат отдельный сценарий для рабочего окружения. Он не запускается обычным `npm run test:browser` и требует явные `E2E_BASE_URL`, `E2E_ALLOW_WRITES=1`, `E2E_RUN_TAG`, `E2E_COMPANY_EMAIL`, `E2E_COMPANY_PASSWORD`, `E2E_DEVELOPER_EMAIL`, `E2E_DEVELOPER_PASSWORD`. Используются заранее согласованные подтверждённые тестовые аккаунты. Запуск создаёт помеченный тестовый заказ и отклик, затем выбирает исполнителя; поэтому разрешение на запись обязательно.

```sh
npx playwright test --config playwright.production.config.ts
```

Пароли передаются окружением. Скриншоты, видео и trace отключены; отчёт не печатает значения полей и необработанные ошибки заполнения. Этот сценарий проверяет работу после подтверждённого входа и не заменяет проверку доставки регистрационного письма.
