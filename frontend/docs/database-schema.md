# Соответствие предоставленной схеме БД

Исходные типы интерфейса составлены по таблицам и политикам, присланным владельцем проекта. После объединения веток действующий серверный контракт и ограничения задаются также миграциями в `backend/migrations` и API.

Все предоставленные таблицы описаны в `src/types/database.ts`. Интерфейс использует отдельные модели представления (camelCase, подписи категорий, данные связанных компаний). Эти модели не являются сырыми строками Supabase. Совместимый REST API собирает эти представления; автоматическое подключение таблиц по одной схеме не выполняется.

## Формы

- Профиль: name, bio, skills (в БД text), github_url, avatar_url. Роль, is_moderator, user_id и даты не входят в обновление.
- Портфолио: title, description, project_url; идентификатор владельца должен задаваться доверенной сессией.
- Компания: name, city, category_id, address, phone, email, website_url, source_url. Поля description в таблице нет. Категории выбираются по ID справочника categories. ID демокатегорий не используются как реальные ID в режиме API.
- Заказ: title, description, nullable budget_min/budget_max/deadline. Ноль сохраняется как ноль. Выбор исполнителя задаёт selected_application_id. Черновики и visibility=false исключены из публичных списков.
- Отклик: message, nullable proposed_price/proposed_deadline.
- Контакт: notes, status, contacted_at. Изменение заметки не меняет существующее время contacted_at. Выбор нового дня сохраняется как полдень UTC; updated_at хранится отдельно.
- Обращение: company_id и message; requested_by задаёт сервер из действующей сессии; деморежим использует свой локальный аккаунт. Решение сохраняет resolved_by, resolved_at и resolution_note (в модели UI — reason).
- Журнал модерации хранит записи с action, reason, moderator_id, company_id/order_id и created_at.

Пустые необязательные поля форм преобразуются в null. Числа проверяются на конечность и неотрицательность, календарные даты — на корректность. Старое состояние localStorage мигрирует без сброса пользовательских записей, включая прежний contractorId и текстовый журнал.

## Границы подключения

Backend реализует серверный контракт и проверяет права. К API подключены каталог, заказы и отклики, профиль/аватар/портфолио, избранное и контакты, настройки аккаунта, обзор и карточка компании, управление участниками. Интерфейс модерации, импорта и журнала остаётся демонстрационным и явно закрыт в API-режиме.

Типы `src/types/database.ts` отражают исходную схему. Канонические значения статусов задаются ограничениями миграций; совместимый API преобразует их в модель интерфейса (например, submitted → pending, accepted → selected). companies.visibility имеет тип text, orders.visibility — boolean.

В исходных материалах для company_members была дана только политика чтения. Рабочий сервер проверяет членство и роль, а прямой доступ браузера к таблицам закрыт миграцией. Экран участников позволяет владельцу добавить зарегистрированного пользователя по UUID и удалить участника; сервер запрещает удаление последнего owner. Клиентские ограничения не заменяют серверную авторизацию. История полей профиля описана в profile-schema.md.

`003_profile_avatar.sql` добавляет nullable `avatar_url`, если столбец отсутствует. Рабочий API сохраняет http(s)-ссылку либо проверенный PNG/JPEG/WebP data URL до 256 КиБ и 2048×2048. Отдельное файловое хранилище не подключалось. Режим demo хранит свою копию отдельно в браузере.
