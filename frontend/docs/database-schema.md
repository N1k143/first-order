# Соответствие предоставленной схеме БД

Источник — таблицы и политики, присланные владельцем проекта. Бэкенд, миграции и RLS не изменялись.

Все предоставленные таблицы описаны в `src/types/database.ts`. Интерфейс использует отдельные модели представления (camelCase, подписи категорий, данные связанных компаний). Эти модели не являются сырыми строками Supabase. Будущий REST API должен явно собирать эти представления; автоматическое подключение таблиц по одной схеме не выполняется.

## Формы

- Профиль: name, bio, skills (в БД text), github_url, avatar_url. Роль, is_moderator, user_id и даты не входят в обновление.
- Портфолио: title, description, project_url; идентификатор владельца должен задаваться доверенной сессией.
- Компания: name, city, category_id, address, phone, email, website_url, source_url. Поля description в таблице нет. Категории выбираются по ID справочника categories. ID демокатегорий не используются как реальные ID в режиме API.
- Заказ: title, description, nullable budget_min/budget_max/deadline. Ноль сохраняется как ноль. Выбор исполнителя задаёт selected_application_id. Черновики и visibility=false исключены из публичных списков.
- Отклик: message, nullable proposed_price/proposed_deadline.
- Контакт: notes, status, contacted_at. Изменение заметки не меняет существующее время contacted_at. Выбор нового дня сохраняется как полдень UTC; updated_at хранится отдельно.
- Обращение: company_id и message; requested_by берётся из текущего аккаунта демоверсии. Решение сохраняет resolved_by, resolved_at и resolution_note (в модели UI — reason).
- Журнал модерации хранит записи с action, reason, moderator_id, company_id/order_id и created_at.

Пустые необязательные поля форм преобразуются в null. Числа проверяются на конечность и неотрицательность, календарные даты — на корректность. Старое состояние localStorage мигрирует без сброса пользовательских записей, включая прежний contractorId и текстовый журнал.

## Границы подключения

Рабочая запись пока остаётся демонстрационной. Backend имеет только health endpoint. Предложенные REST маршруты ещё не реализованы; схема БД не заменяет конфигурацию сессии и контракт API.

Значения текстовых status, website_status, visibility и member_role не перечислены в присланной схеме. Нынешние значения — соглашения демоверсии, которые нужно сопоставить с контрактом сервера перед интеграцией. companies.visibility имеет тип text, orders.visibility — boolean.

Для company_members дана только политика чтения, поэтому управление участниками недоступно. Для компаний, категорий, заказов, откликов и модерации политики записи не предоставлены; право редактирования должно проверяться сервером. Клиентские ограничения не заменяют RLS. Особенности profiles_update_own описаны в profile-schema.md.

avatar_url предусмотрен схемой, но загрузка файлов в хранилище ещё не подключена. В демоверсии файл хранится как data URL в браузере; рабочий сервис должен сохранять URL загруженного файла.
