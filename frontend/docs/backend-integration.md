# Связь фронтенда с сервером

## Действующий контракт

Go backend реализует Supabase Auth, профили, каталог, заказы, отклики, модерацию и импорт. Канонический контракт использует `/api/v1` и snake_case; совместимые маршруты возвращают модели текущего интерфейса. Полный перечень и правила доступа — в [backend/README.md](../../backend/README.md).

Next.js передаёт `/health` и `/ready` в backend, `/api/v1/*` — в канонический API, `/api/*` — в совместимый API и Auth. `BACKEND_URL` используется только сервером; в локальной разработке по умолчанию `http://127.0.0.1:18080`. Рабочая схема портов описана в [deploy/README.md](../../deploy/README.md).

## Режимы данных и сессия

`NEXT_PUBLIC_DATA_MODE=demo` включает локальные примеры; `api` включает реальные запросы без подстановки демонстрационных данных при ошибках. Значение входит в сборку. В API-режиме состояние начинается пустым, `/me` загружает профиль и членство в компаниях. Роли и доступ к данным проверяет сервер.

Сессия хранится в HttpOnly cookies. Клиент отправляет cookies на тот же origin, после `401` выполняет одно общее обновление сессии для параллельных запросов и повторяет каждый запрос не более одного раза. Для изменяющих запросов с cookies backend проверяет Origin. Пароли и токены не сохраняются в localStorage.

Регистрация, подтверждение email, повторная отправка, вход, выход, смена email, восстановление и смена пароля, callback обслуживаются Go API через Supabase. Для отправки писем требуются SMTP и разрешённый callback `/auth/callback`; на рабочем сайте это уже настроено.

## Подключённые сценарии

Каталог и карточки компаний, заказы, отправка исправлений и полный цикл заказа используют сервер. Подключены также обзор личного кабинета, просмотр и редактирование профиля/аватара, CRUD портфолио, отдельные избранное и история контактов, настройки email/пароля, обзор компании, её карточка и участники. После успешных мутаций состояние и открытые ресурсы перечитываются; сбой сохранения не объявляется успехом.

## Контракты дополнительных разделов

- Профиль: `PATCH /api/v1/me/profile`, поля `name`, `bio`, `skills`, `github_url`, `avatar_url`; nullable-поля принимают `null`, пропущенные сохраняются. `/api/me` возвращает модель с `avatarUrl`.
- Портфолио: `/api/v1/me/portfolio` и `/api/v1/me/portfolio/{id}`; автор определяется сессией, чужие изменения запрещены.
- Избранное и контакты: `/api/v1/me/favorites` и `/api/v1/me/company-contacts`; список и изменение принадлежат текущему пользователю.
- Email: `POST /api/auth/change-email` с `{email}`; `confirmation_required` означает ожидание писем, `updated` — уже подтверждённый адрес. Первое подтверждение безопасной смены может вернуть `second_confirmation_required`; до второй ссылки новая сессия не создаётся.
- Пароль: `POST /api/auth/reset-password` с `{password,confirm}`, включая обычную действующую сессию из настроек.
- Компания и участники: серверное членство определяет доступную компанию. Изменение карточки использует `/api/v1/companies/{id}`; владелец добавляет зарегистрированного пользователя через `POST /api/v1/companies/{id}/members` с `{user_id,member_role}` и удаляет через `DELETE .../members/{user_id}`. Роли членства — `owner` и `representative`; последний владелец защищён ответом `409`.

Канонические коллекции сохраняют `{items,total,page,limit}`. Compatibility `/categories`, `/orders`, `/me/applications`, `/me/portfolio` и списки откликов/участников разворачивают `items` в массив. Frontend нормализует оба формата коллекций для обновлений сервера без одновременного переключения всех клиентов.

## Оставшиеся демонстрационные экраны

Модерация, импорт и журнал модерации пока закрыты в API-интерфейсе явным сообщением. Серверные операции для них существуют, но их новые формы ещё не подключены. Добавление участника не является email-приглашением; загрузка произвольного файла импорта не имитируется.

Текущий статус проверок — в [implementation-status.md](implementation-status.md).
