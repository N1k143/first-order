# Управляемый сбор: контракт для кабинета модератора

Требуется миграция `007_collection_jobs.sql` и работающий процесс Go API. Фронтенд реализуется отдельно. Все пять маршрутов доступны только модератору; гость получает `401`, обычный пользователь и `IMPORTER_TOKEN` — `403`. Для cookie-сессии POST требует разрешённый `Origin`.

## Запуск

`POST /api/v1/collection/jobs`

```http
Idempotency-Key: 03ca2879-4f40-43ce-87c1-a148fa5b508c
Content-Type: application/json

{"kind":"collect","limit":20}
```

`collect` получает следующую порцию новых OSM-объектов Астаны, исключая все уже известные source IDs, включая отклонённые. Категории чередуются. `recheck` проверяет сайты существующих pending-кандидатов без ручных правок, проверенных более суток назад, начиная с самых старых; новый запрос к Overpass не выполняется. `limit` обязателен, от 1 до 100. Город и источник фиксированы сервером; произвольные URL, пути, ключи поставщиков и команды не принимаются.

Новый запуск возвращает `202` и объект задания. Повтор того же ключа с теми же параметрами и автором возвращает тот же объект с `200`, включая завершённое задание. Изменение параметров при том же ключе — `409 IDEMPOTENCY_CONFLICT`. Для новой операции нужен новый UUID.

Одновременно допускается одно pending/running-задание: `409 COLLECTION_ACTIVE` при попытке создать второе. Повторная проверка одной карточки допускается не чаще раза в сутки. Если очередь recheck пуста — `409 NO_CANDIDATES`. Запросы к публичному Overpass допускаются не чаще одного раза в час, включая неудачные попытки; отложенный запуск остаётся `pending`, точное время — `available_at`. Планировщик периодического массового сбора не включён. Это ограниченный ручной сбор, а не гарантия полного покрытия города.

## Прогресс и история

| Маршрут | Ответ |
|---|---|
| `GET /api/v1/collection/jobs?page=1&limit=20&status=running` | Стандартные `items,total,page,limit`; status необязателен |
| `GET /api/v1/collection/jobs/{id}` | Задание, `events` и `results` |
| `POST /api/v1/collection/jobs/{id}/cancel` | Запрос отмены, `202`; завершённое задание — `200` без изменения |
| `POST /api/v1/collection/jobs/{id}/retry` | Повтор failed-задания, `202`, либо `409` |

Для cancel/retry тело не требуется. Неизвестный UUID задания — `404`; некорректные параметры — `422`.

Поля задания: `id,kind,source,city,requested_limit,status,created_by,attempt,processed,total,saved,skipped,found,needs_review,error_code,cancel_requested,available_at,created_at,started_at,finished_at,updated_at`. Время передаётся в UTC. `created_by=null` означает запуск оператором с сервера, без пользовательской сессии.

Статусы: `pending → running → completed/failed/canceled`. `total=0` до получения исходного списка; затем `processed/total` отражает сохранённые контрольные точки. Пустая новая порция завершается с `completed,total=0`. `saved+skipped=processed`: skipped означает защиту изменённой/рассмотренной карточки, а не ошибку сети. `found+needs_review=processed` описывает результаты проверок, включая skipped. После отмены уже сохранённые результаты остаются; незавершённая проверка не сохраняется.

`results` содержит до 100 объектов: `item_index` (с нуля), `external_id,name,website_status,reason,saved,checked_at`. Сетевая ошибка сайта записывается как `needs_review` с причиной, а не как отсутствие сайта. Полная история URL и доказательства доступны в соответствующей карточке `/api/v1/imports/candidates`. Для skipped исходный payload не изменяется, результат попытки виден в задании. Отсутствие сайта автоматически не утверждается.

`events` отсортированы по возрастанию `id`: `created,started,cancel_requested,retry_requested,worker_recovered,completed,failed,canceled`; содержат `actor_id` и время. Серверные события имеют null actor. Ошибки задания: `SOURCE_UNAVAILABLE`, `SOURCE_INVALID`, `CHECKPOINT_FAILED`, `WORKER_INTERRUPTED`, `JOB_TIMEOUT`. Детали соединений и секреты не выдаются. Общий предел попытки — 30 минут.

Интерфейс может опрашивать активное задание раз в 3–5 секунд. При `cancel_requested=true` показывать ожидание отмены до терминального статуса. Повтор разрешён только для `failed`, максимум три попытки суммарно; при `409 RETRY_UNAVAILABLE` необходимо разобраться с причиной. Повтор продолжает сохранённый список с `processed`, не проверяя завершённые элементы заново. Если исходный список ещё не получен, повтор ждёт ограничения частоты источника.

## Сохранность данных и эксплуатация

Сетевые запросы выполняются вне транзакций. Жизнеспособность рабочего процесса проверяется каждую секунду; аренда задания — две минуты. После её истечения другой процесс продолжает работу с контрольной точки. Старый процесс теряет право записи. После трёх прерываний задание становится `failed`. Контрольная точка, результат проверки и запись кандидата фиксируются одной транзакцией.

Автоматически изменяются только pending-кандидаты с пустым draft; recheck дополнительно сравнивает revision, сохранённую при запуске. Одобренные, отклонённые и опубликованные компании, ручные правки и история модерации сохраняются. Публикация остаётся отдельным действием модератора. Существующий CSV `/imports` работает независимо.

Сохраняются ограничения сборщика: robots.txt, безопасные публичные HTTP(S)-адреса, ограниченные ответы/редиректы, последовательные проверки, бесплатные источники OSM/Wikidata/email domain. Источники и атрибуция сохраняются. Прямой доступ browser/PostgREST к служебным таблицам закрыт.

Оператор может поставить такое же задание с сервера из `backend/`, используя приватное окружение с `DATABASE_URL`:

```sh
go run ./cmd/queue-collection --kind=collect --limit=10 \
  --request-key=03ca2879-4f40-43ce-87c1-a148fa5b508c
```

Команда только ставит задание; обработку выполняет запущенный API. Её доступ определяется серверными правами к базе. Не используйте пример UUID повторно для разных операций. Старый `cmd/collect-companies` остаётся инструментом разового офлайн-пилота, не использует управляемую очередь и её ограничитель частоты; для штатной работы используйте новую очередь.
