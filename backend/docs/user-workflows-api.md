# Пользовательские сценарии: серверный контракт

Миграция `008_user_workflows.sql`. Все приведённые маршруты используют действующую пользовательскую сессию; `IMPORTER_TOKEN` их не открывает. Все пути начинаются с `/api/v1`. Cookie-запросы POST требуют разрешённого `Origin`. Новые экраны и кнопки подключает разработчик фронтенда.

## Заказ и отклики

| Шаг | Запрос | Результат |
|---|---|---|
| Создать черновик | `POST /orders` | `201`, status `draft`; требуется членство в компании |
| Опубликовать | `POST /orders/{id}/publish` | `200`, status `open` |
| Откликнуться | `POST /orders/{id}/applications` | `201`, status `submitted`; только разработчик, не участник компании-заказчика |
| Изменить предложение | `PATCH /applications/{id}` | Только автор submitted-отклика |
| Отозвать | `POST /applications/{id}/withdraw` | Только автор; status `withdrawn` |
| Отклонить отдельный отклик | `POST /applications/{id}/reject` | Участник компании; submitted → rejected, заказ остаётся открытым |
| Выбрать исполнителя | `POST /orders/{id}/select-application` с `{"application_id":"UUID"}` | Выбранный submitted → accepted, остальные submitted → rejected; заказ → contractor_selected |
| Получить контакты | `GET /orders/{id}/participants` | Только компания-заказчик и выбранный разработчик |
| Завершить работу | `POST /orders/{id}/complete` | Только участник компании; contractor_selected → completed |
| Отменить заказ | `POST /orders/{id}/close` | draft/open/contractor_selected → closed; участник компании или модератор |

Тела publish/withdraw/reject/complete/close пустые либо `{}`. Посторонние поля отвергаются. Повтор успешных publish, complete, close, withdraw и reject возвращает `200` с текущим объектом без повторных побочных действий. Выбор того же исполнителя повторно возвращает `200` для contractor_selected/completed. Повторная авторизация всегда выполняется: потерявший членство пользователь больше не может управлять заказом. Другой выбор, уже отозванный/принятый отклик, завершение до выбора и изменение терминального состояния дают `409`.

Повторная отправка нового отклика остаётся `409 APPLICATION_ALREADY_EXISTS`, в том числе после отзыва/отклонения. Запрет дублей при создании черновика не добавлен: UI должен блокировать повторную отправку формы до ответа. Публикация проверяет актуальность срока. Принятый отклик остаётся `accepted` после завершения или отмены заказа — это история выбора, а не текущее состояние работы.

Все ответы с откликами дополнены:

```json
{"status":"accepted","order_status":"completed","order_visibility":true,"is_selected":true}
```

Статус работы нужно брать из `order_status`. `is_selected` показывает историческую связь с заказом. Канонические статусы откликов — submitted/accepted/rejected/withdrawn. Старый адаптер `/api/...` сохраняет прежние camelCase-поля; accepted-отклик завершённого заказа выдаёт frontend-статус `completed` вместо `selected`.

После закрытия submitted-отклики отклоняются, accepted и выбранный ID сохраняются. Участники компании, выбранный исполнитель и модератор видят историю заказа через существующие маршруты. Остальные разработчики видят собственный отклик и его `order_status`, не получают доступ к чужим предложениям или приватным контактам. Скрытие модератором не меняет жизненный цикл заказа.

## Контакты после выбора

`GET /orders/{id}/participants` возвращает:

```json
{
  "order_id":"UUID",
  "status":"contractor_selected",
  "company":{"id":"UUID","name":"Компания","email":null,"phone":null},
  "customer":{"user_id":"UUID","name":"Заказчик","email":"customer@example.com"},
  "contractor":{"user_id":"UUID","name":"Исполнитель","email":"developer@example.com","github_url":null}
}
```

Email участников берётся из их текущих аккаунтов Auth; customer — автор заказа. Контакты компании берутся из её карточки. Интерфейс должен пояснять при выборе, что после выбора стороны получают контактные email друг друга. Доступ есть у выбранного исполнителя и текущих участников компании только для contractor_selected/completed. До выбора, после закрытия, для других откликнувшихся и для модератора без членства — `404`; для гостя — `401`. Публичная видимость заказа/компании не открывает контакты. Ответ имеет `Cache-Control: private, no-store`.

## Личные кабинеты

`GET /me/workspace` — сводка текущего пользователя одним запросом:

```json
{
  "companies":1,
  "orders":{"total":2,"draft":0,"open":1,"contractor_selected":0,"completed":1,"closed":0},
  "applications":{"total":1,"submitted":0,"accepted":1,"rejected":0,"withdrawn":0},
  "work":{"total":1,"in_progress":0,"completed":1,"closed":0},
  "favorites":0,"contacts":0,"portfolio":0,"unread_notifications":2
}
```

orders учитывает все заказы всех компаний текущего пользователя, без ограничения первой страницей; applications — только его отклики; work — только заказы, где он выбран. Favorites считает доступные опубликованные компании. Нулевые разделы возвращаются с нулями, а не отсутствуют.

`GET /me/work?status=completed&page=1&limit=20` — выбранные для пользователя заказы, включая скрытые и историю отменённых. Status необязателен: contractor_selected/completed/closed. Стандартный ответ `items,total,page,limit`; сортировка по updated_at DESC, id DESC. Чужих назначений нет.

`GET /me/company-applications?company_id=UUID&status=submitted&page=1&limit=20` — общий список откликов на заказы компаний пользователя, без отдельных запросов на каждый заказ. Оба фильтра необязательны; status — submitted/accepted/rejected/withdrawn. Сортировка created_at DESC, id DESC. Чужой company_id даёт `403`, отсутствие членства без фильтра — пустой список. Модератор не получает чужой кабинет через этот маршрут; для него остаются отдельные маршруты модерации.

## Уведомления внутри сервиса

| Событие | Получатель |
|---|---|
| application_submitted | Текущие участники компании |
| application_withdrawn | Текущие участники компании |
| application_accepted | Выбранный разработчик |
| application_rejected | Отклонённый разработчик, включая выбор другого и закрытие заказа |
| order_completed | Выбранный разработчик |
| order_closed | Выбранный разработчик при отмене после выбора |

Уведомления создаются для новых действий после выкладки. Старые решения не рассылаются повторно. Автор действия не получает уведомление самому себе. Изменение состояния и уведомление сохраняются одной транзакцией; сбой уведомления откатывает действие. Повторные и конкурентные запросы не создают дублей одного события.

- `GET /me/notifications?unread=true&page=1&limit=20` — `items,total,page,limit,unread_count`; unread необязателен. `total` учитывает фильтр, unread_count — весь непрочитанный остаток пользователя.
- Элемент: `id,event,order_id,application_id,actor_id,order_title,company_name,created_at,read_at`. Названия сохраняются на момент события: бывший участник компании не видит будущие изменения через старое уведомление.
- `POST /me/notifications/{id}/read` — `200` с id/read_at; повтор сохраняет первоначальное время прочтения. Чужой ID — `404`, в том числе для модератора.
- `POST /me/notifications/read-all` — `200 {"updated":N}`; только непрочитанные уведомления текущего пользователя на момент запроса. Повтор без новых уведомлений даёт 0. Тело пустое либо `{}`.

Уведомление — история события; актуальное действие и права нужно проверять при открытии заказа/отклика. События от удалённых заказов/откликов удаляются каскадно. Прямой доступ browser/PostgREST к таблице закрыт.

## Проверки

На отдельной PostgreSQL проверяются полный цикл с рабочей ролью БД, отдельный отказ, конкурирующие выбор/отказ, отмена, повтор действий, обмен контактами, изоляция кабинетов и уведомлений, отметки прочтения и откат отклика при ошибке сохранения уведомления. Также выполняются существующие проверки регистрации/сессий, профиля/портфолио, избранного, контактов, модерации и сбора.
