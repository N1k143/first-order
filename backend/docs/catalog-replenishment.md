# Автоматическое пополнение каталога

После миграции `009_catalog_replenishment.sql` Go API поддерживает запас компаний без отдельного cron. Реализация относится только к бэкенду. Автопополнение включено по умолчанию: минимум 20 карточек, цель 50, партия до 25, очередь модерации до 100, интервал между постановками не менее 24 часов. Настройки и состояние хранятся в PostgreSQL и переживают перезапуск.

## Что считается доступным

Опубликованная компания с точным городом `Астана` и `website_status=not_found` либо `needs_review`. Компании с найденным сайтом, скрытые карточки и другие города не учитываются. `needs_review` означает необходимость проверки, а не доказанное отсутствие сайта. Избранное и просмотр карточки не уменьшают запас; наличие заказа также не является признаком недоступности компании. Участие компании в заказах и согласие на сотрудничество эта метрика не оценивает.

При количестве **не больше minimum** включается пополнение до target. Этот режим сохраняется, даже когда запас поднялся выше minimum; достижение target выключает его. При запасе между минимумом и целью без ранее начатого пополнения сбор не запускается.

Все pending-кандидаты OSM учитываются как ожидающий проверки буфер, включая карточки с ручным черновиком и найденным сайтом. Это консервативный ограничитель нагрузки, не обещание публикации каждого кандидата. Если буфера достаточно для достижения цели, система ждёт модерацию. Модератор должен одобрять подходящие карточки и отклонять неподходящие, иначе очередь может блокировать новые сборы.

Лимит новой партии — минимум из batch_size, недостающего запаса с учётом pending и свободного места до pending_limit. Одновременно допускается только одно pending/running-задание, включая ручной сбор и recheck. Ручные задания имеют собственные ограничения; pending_limit ограничивает автоматический сбор, а не действия оператора.

## Источник и публикация

Используется штатный `osm_astana`, с существующим поиском новых source IDs, проверкой сайта, лицензией и атрибуцией OSM. Автоматический сбор не использует экспериментальный парсер 2ГИС; его подключение потребует отдельной интеграции источника и определения условий использования данных. Это не гарантия полного покрытия города.

Результаты поступают в `/api/v1/imports/candidates` в статусе pending. Публикация — отдельное действие модератора. Скрытые компании не возвращаются автоматически, ручные черновики и решения не перезаписываются. В заданиях автоматический запуск отмечен событием `automatic_replenishment`, `created_by=null`. Внутренний ключ задания не выдаётся наружу.

## API для модератора

| Метод и маршрут | Назначение |
|---|---|
| `GET /api/v1/collection/replenishment` | Настройки, текущие counts.available/counts.pending, состояние, последнее задание |
| `PATCH /api/v1/collection/replenishment` | Изменить настройки с защитой от потери одновременных изменений |
| `GET /api/v1/collection/replenishment/history?page=1&limit=20` | История настроек: автор, время, before_policy/after_policy |

Гость — 401; обычный пользователь и IMPORTER_TOKEN — 403. Cookie-запрос изменения требует разрешённого Origin. Посторонние поля отклоняются. Прямой доступ anon/authenticated к таблицам закрыт. Фронтенд в этой задаче не меняется.

Пример PATCH:

```json
{
  "expected_revision": 1,
  "enabled": true,
  "minimum": 20,
  "target": 50,
  "batch_size": 25,
  "pending_limit": 100,
  "cooldown_hours": 24
}
```

Все настройки, кроме expected_revision, необязательны; необходимо хотя бы одно изменение. Успех — 200 и новые настройки с увеличенной revision. Устаревшая expected_revision — 409 REVISION_CONFLICT; перечитать GET и повторить осознанное изменение. Неверные значения — 422. Диапазоны: minimum 1–10000; target больше minimum и до 20000; batch_size 1–100; pending_limit 1–1000; cooldown_hours 1–168.

`enabled=false` останавливает будущие постановки. Уже созданное задание отменяется отдельно через `POST /collection/jobs/{id}/cancel`. Изменение настроек не обнуляет накопленную паузу источника или очереди.

GET также возвращает `source`, `city`, `automatic_publication=false`, `check_interval_seconds=300`, `refill_active`, `last_checked_at`, `next_check_at`, `next_run_at`, `last_job_id`, `last_job` при наличии. counts вычисляются на момент запроса; last_reason относится к last_checked_at.

| last_reason | Значение |
|---|---|
| stock_sufficient | Запаса достаточно, режим пополнения не активен |
| disabled | Автоматические постановки выключены |
| collection_active | Уже выполняется или ожидает задание |
| pending_limit | Очередь модерации достигла предела |
| awaiting_moderation | Ожидающих кандидатов достаточно для достижения цели |
| cooldown | Следующая партия ждёт next_run_at |
| queued | Создано автоматическое задание |

Проверка выполняется при старте и затем примерно каждые пять минут (пробуждение процесса каждые 30 секунд; next_check_at общий для всех экземпляров). Короткая транзакция и общая advisory-блокировка с ручным управлением обеспечивают одну постановку. HTTP выполняет существующий worker вне транзакции.

Ограничитель источника не позволяет получать OSM чаще раза в час, включая ошибки. После ошибочной либо завершённой без сохранённых карточек автоматической партии следующие попытки откладываются на 2, 4, 8 базовых интервалов с потолком 168 часов. Успешная партия сбрасывает серию; отмена прерывает серию, но не отменяет уже установленный next_run_at. Перезапуск API эти ограничения не обходит. Сбой и пустой источник видны в last_job и обычной истории заданий. Уведомления во внешние каналы не подключены.

При установке на существующую рабочую базу миграция не публикует и не изменяет компании. После запуска API первая проверка оценивает текущий запас и очередь. Резервное копирование deploy/ops.py автоматически включает обе новые таблицы, так как составляет список таблиц из базы.
